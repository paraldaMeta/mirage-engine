# vork 與 67js：拆代碼筆記，對 mirage 有用的地方

2026-11-10。讀的版本：
- vork：`voyager-so/vork` @ `8de8c2e`
- 67js：`codepawl/67.js` @ `76510af`（npm `@codepawlhq/67js` 0.17.0）

兩個倉庫都只 clone 到暫存區閱讀，沒有建置，也沒有執行它們的代碼。

## 兩者是什麼

| | vork | 67js |
|---|---|---|
| 定位 | 離線、無頭的 3D／VFX 渲染器，agent 寫 scene JSON 和 Slang 著色器 | WebGL2 引擎，agent 透過 23 個 MCP 工具建場景、看圖、匯出 |
| 技術 | Rust + Slang，Vulkan／Metal，硬體光追，另有路徑追蹤 | 自寫 WebGL2 渲染器，在 Chrome 裡跑 |
| 授權 | **Preview License，source-available**：可讀可用，不可散布修改版 | **MIT**：可以搬代碼，NOTICE 裡要寫明出處 |
| 與 mirage 的距離 | 遠：離線電影渲染，不是即時遊戲 | 近：瀏覽器、JS、agent 驅動 |

## 先說結論：渲染核心沒什麼可搬

- **67js 自己的量測顯示 three.js 更快。** `bench/runtime/README.md` 記錄：在 SwiftShader 上，67js 每幀是 three.js 的 2.2–5.1 倍。GPU 上 7 個場景裡，67js 只贏 2 個。它唯一大幅領先的場景，靠的是自動 LOD 加視錐剔除。mirage 已經有一樣的做法：`packages/core/src/lod.js`，用 meshoptimizer、誤差小於一個像素。
- **67js 的 `scene_walkmap` 是 CPU 射線網格。** mirage 的 `packages/play/src/walkgrid.js` 是 GPU 分層烘焙加環繞數，會走的範圍更廣。
- **67js 的連拍對照圖加標籤，mirage 的 `snap.mjs` 已經有。** 畫面閃爍檢查 mirage 也有：`playtest` 的 `flicker`。
- **vork 和 mirage 不是同一類東西。** vork 是離線光追和路徑追蹤，mirage 是 60 Hz 瀏覽器遊戲。它的渲染技術沒法直接用。

值得學的是另一層：**怎麼讓 agent 自己發現畫面錯了**。

## 建議，按價值排

### 1. 每個鏡頭寫明「該看見什麼」，自動檢查（高價值，中等工作量）

- **起因。** A1 的 A 場就漏在這裡：「實心欄杆」那一格看不到欄杆，但機器檢查全部通過。這只有人看圖才發現。
- **67js 的做法。** `src/frame-checks.js`，約 150 行，MIT。每格畫面跑幾項便宜的檢查：
  - 畫面是空的；
  - 主體出框，或在畫面裡太小（小於 5%）；
  - 幾乎全黑（98% 像素的亮度低於 5/255）；
  - 過曝（35% 像素高於 250/255）。

  每項給一個 `fix`，寫明要改哪個欄位、試什麼值。
- **vork 的做法。** 可以輸出 `object_index` 通道：每個像素屬於哪個物件。這只能借想法，不能搬代碼。
- **mirage 可以怎麼做。**
  - 在 `snap.mjs` 的鏡頭和 playtest 的步驟上加 `expect: { visible: ["rail", ...], minShare }`。
  - 把具名物件用純色各畫一張 ID 圖，算出每個物件佔多少像素。
  - 不到門檻就判失敗，並寫出原因（被擋住、出框或太小）。
  - 再加上黑屏和過曝兩項檢查，可以直接照 67js 的門檻。

### 2. 載入時靜態掃描共面 z-fight（中價值，中等工作量）

- **mirage 現在的做法。** 共面問題只靠兩樣：`flicker` 沿著走的路徑採樣，以及技能文件裡那句「錯開 1–2 cm」。路徑沒經過的共面不會被發現。
- **67js 的做法。** `src/coplanar-overlap.js`，約 520 行，MIT。它在載入時找出「同一平面、同一朝向、有重疊面積」的物件對。工作量有固定上限（先用網格篩，再只比較兩者包圍盒交集內的三角形）。每對都附修法。
- **mirage 可以怎麼做。** 移植到 `world/check` 或 playtest，報出物件名稱對和重疊面積。

### 3. 統一診斷格式（低工作量）

- 67js 的每條警告都是 `{kind, severity, target, message, fix}`。
- vork 的錯誤按類別給退出碼：2 用法、3 場景無效、4 裝置、5 檔案 IO。每個輸出檔旁邊還有 `meta.json`，裡面的 `warnings` 列出被悄悄省略或替換的效果。
- mirage 的 `playtest`、`world/check`、`validate-plan` 各有各的格式。統一成一種之後，agent 只要學一次。
- 「品質檔位降級時有沒有悄悄關掉陰影之類的效果」這點我沒查證，要先查。

### 4. 小型、可重複的 agent 任務集（高價值，工作量大）

- **mirage 現在的做法。** A1 是每個客戶端跑一次大任務，樣本太少，看不出某次技能修改有沒有幫助。
- **67js 的做法。** `bench/agent-modeling/` 有三十多個小任務，每個都有：
  - 機器檢查：只看產出，不看過程；
  - 一份參考解，測試要求它必須通過；
  - 故意弄壞的變體，測試要求它們必須失敗，以免是檢查本身寫錯；
  - 輪廓重疊分數：三個固定正交鏡頭，算 IoU；
  - 盲評提示詞，交給視覺模型打分。

  每次記錄工具呼叫次數、錯誤數、token 和耗時。三處小摩擦修好後，工具呼叫從 39 次降到 17 次。
- **mirage 可以怎麼做。** 挑 5–10 個 mirage 的小任務，例如：
  - 放一道會擋人的牆；
  - 加一個可互動的門；
  - 把小徑接到河灣。

  機器檢查用現有的 playtest。每次改技能前後各跑一輪，比較結果。

### 5. 給技能包設字數上限（低工作量）

- vork 的 `vork help` 分層：首頁 → 主題 → `--all` → 單一欄位查詢。API 摘要從 schema 自動生成，並有工具量測說明的大小。它宣稱核心 API 約 2,500 token。
- mirage 七個 `SKILL.md` 合計約 35 KB。可以在 `agent/check.mjs` 加一個總量上限，只准減不准漲；超出就要求把內容移到 `references/`。

## 不建議學的

- **67js 的 checkpoint／branch／revision 一套。** 它的 agent 透過 MCP 改場景狀態，所以需要這套。mirage 的 agent 是改代碼，git 已經提供相同的功能。
- **把 mirage 包成 MCP 伺服器。** 67js 的數據有參考價值：6 個任務，MCP 平均 3.2 次呼叫、24 秒；直接寫 three.js 代碼平均 8.8 次、359 秒，而且大部分時間花在讓無頭 Chrome 寫出 PNG。但它的 token 反而更多（375k 對 269k）。mirage 的 `playtest` 和 `snap` 已經解決了「出圖難」。要不要做 MCP，應該等任務集（建議 4）有數據再決定。
- **兩家的效能宣傳數字。** 例如「一百萬隻鳥 97 秒」，是 vork 在 NVIDIA L4 上自己量的，我沒有重現。

## 授權注意

- 67js 是 MIT。搬 `frame-checks.js` 或 `coplanar-overlap.js` 可以，但要在 NOTICE 寫明出處和版本。
- vork 的 Preview License 禁止散布修改版，也禁止轉授權。只能借想法，**不能**把它的代碼或著色器抄進 mirage。

# 補充：google/three-live

2026-11-10。讀的版本：`google/three-live` @ `45dcc84`，Apache 2.0 授權：可以搬代碼，要保留授權聲明並寫進 NOTICE。

它把 AI 寫的 three.js 代碼即時編譯成原生格式（Android 上的 Filament、蘋果的 RealityKit）和 WebGL2／WebXR。主要部件：
- Rust 寫的編譯器和空間 linter（TL100–TL504）；
- 四視圖對照圖（相機、正面、頂視、等角，帶網格）；
- 一套 agent 評測：「不給指引」和「給指引」兩組各 100 個腳本，加上一輪依診斷自動修復，再交給視覺模型評分。

它的渲染層是自己寫的 WebGL2 和 WebGPU，不是 three.js 的渲染器。

## 執行期：陰影只在需要時重畫（實測值得做）

- **three-live 的做法。** `shadow-maps.ts` 把投影物的狀態算成一個雜湊值（FNV-1a），雜湊沒變就不重畫陰影圖。鏡頭不動時，陰影深度圖的渲染次數是 0。
- **mirage 現在的做法。** `renderer.shadowMap.autoUpdate` 保持預設的 true，所以每一幀都重畫 2048² 的太陽陰影。
- **實測。** 這台測試機，medium 檔位，1440×900，每幀 240 次取中位數，各跑三輪：

| 範例 | 每幀重畫陰影 | 不重畫 | 差 |
|---|---|---|---|
| woodland-path | 3.3–3.5 ms | 3.0–3.1 ms | 約 0.3 ms（9%） |
| river-ford | 3.2–3.3 ms | 3.0 ms | 約 0.2–0.3 ms（7%） |
| walled-garden | 3.7–3.8 ms | 3.2–3.4 ms | 約 0.4–0.5 ms（13%） |

- **不能直接關掉。** 風吹的樹葉有陰影（`mat.depth` 帶風的頂點 hook），角色和可移動物件也會動。
- **可行的做法。**
  - 只在三種情況下標記陰影需要重畫：投影物的矩陣變了、太陽移動了（`fitShadow` 已經會標記）、或有帶風 hook 的投影物。
  - 帶風的陰影可以降到 30 Hz 重畫，或把它們拆到另一張較小的陰影圖。
  - 驗收要量兩件事：省下多少時間，以及用 `still-identity` 確認靜止畫面一個像素都沒變。

## 給 agent 的檢查

1. **四視圖對照圖。**
   - **三-live 的做法。** `render --view=quad --grid --annotations` 一次輸出四個視角：相機、正面、頂視、等角，帶公尺網格和標籤。
   - **mirage 現在的做法。** `snap` 只拍計畫裡的視點，都是人眼高度。
   - **為什麼要加。** 縫隙、物件重疊、懸空，從人眼高度不容易看出來。
   - **mirage 可以怎麼做。** 給 `snap` 加 `--views quad`：多一張頂視正交圖（帶網格、模組名和 `plan.bounds` 框）和一張等角圖。
2. **場景靜態 lint。** three-live 的規則都用包圍盒算，成本低：
   - TL302：相機在不透明網格裡面。mirage 可以拿 walk grid 檢查每個視點和出生點是不是在實心物件裡。
   - TL303：物件完全出框。mirage 的 `see` 用像素算，還考慮遮擋，比它準。
   - TL304：比例不對（小於一個像素，或大得離譜）。
   - TL306：兄弟物件互相穿插或共面。這和先前第 2 條「共面 z-fight 掃描」是同一件事。
   - TL307：應該站在地上的東西懸空或陷進地裡。mirage 可以用 `play.grid.groundAt` 檢查物件底部離下方地面多遠，做一個通用的懸空檢查；目前懸空只能靠人看圖。
3. **診斷能不能讓 agent 一輪修好。** three-live 的評測把診斷（代碼、行號、`Hint`）交給模型修一輪，量修復率，比較的是「給指引」和「不給指引」兩組。這可以併進第 4 條的 agent 任務集：用 mirage 的 playtest 失敗訊息做同樣的量測。
4. **偵測被悄悄丟掉的功能。** three-live 的評測會找出被悄悄替換的寫法，例如換成 `BoxGeometry` 或空的代理物件。mirage 對應的問題是：品質檔位降級時，有沒有悄悄關掉某些效果。這點和 vork 的 `warnings` 是同一個問題，還沒查證。

## 不建議學的

- **WebGPU render bundle。** mirage 建在 three.js 的 WebGL2 上，換 WebGPU 是大工程。目前每幀 3–4 ms，沒有這個需要。
- **沙盒執行 AI 代碼。** mirage 的 agent 改的是本機代碼，不是在使用者的瀏覽器裡跑模型即時寫的腳本。
- **按 bundle 設大小上限。** mirage 已經有 `plan.budget.singleFileMB` 和 `test:pack`。
